# Hostinger review and rollback checklist

Not approved for production release. Do not deploy or activate indexing during this task. Local type, lint, build, full regular regression, route and representative responsive/keyboard checks passed. Review the QA report for exact results, 12 existing opt-in skips and outstanding isolated integration/manual acceptance.

1. Review the working-tree diff, audit matrix, publication manifest and owner approvals. Preserve existing registration/payment/admin switches and unpublished assets.
2. Use Node 22.22.2 (the machine default 22.20.0 is below installed jsdom requirements), run npm ci from the lockfile, then npm run type-check, npm run lint, npm test and npm run build. Resolve every failed or interrupted required check.
3. Supply an isolated staging database, independently generated staging keys, approved test recipients and SMTP credentials in a private environment file. The sanitized .env.staging.example intentionally fails preflight until provisioned. Run the existing disconnected staging preflight before any networked execution. Never use production student records for tests.
4. Verify enquiry input errors, durable acceptance, OTP, rate limiting, queue retry/idempotency and controlled SMTP receipt. Verify valid/invalid/revoked certificate fixtures and admin authorization. Local mocked tests do not prove real delivery or database integration.
5. On approved staging repeat the 37 public course, seven department and seven hidden-404 crawl; verify robots, canonical, HTML/HTTP noindex, sitemap, schemas, security headers and CDN behavior. Run fresh desktop/mobile Lighthouse and keyboard, focus, responsive and social-image review.
6. Preserve the prior known-good Hostinger artifact, environment configuration and established database backup. Keep credentials out of source/archives. The existing scripts/package-hostinger-v8.py requires genuine deployment-output/validation-report-v8.json evidence and refuses archive overwrite. Do not fabricate that input. No release archive has been generated for this candidate.
7. Obtain management release/publication/privacy/certificate/training-crawler approval and hosting sign-off before a separately authorized production deployment. Search activation is a separate explicit decision. Use owner-managed Google/Bing accounts for submissions.
8. After release verify the origin and cached responses again. On regression restore the previous known-good code artifact and matching environment switches, clear only the necessary CDN cache and recheck health/routes/noindex. Preserve enquiry/student records. Do not delete records, reverse migrations blindly or rerun provisioning merely to roll back code. No schema migration was introduced by this remediation.
